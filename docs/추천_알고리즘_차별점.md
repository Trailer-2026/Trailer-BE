# AI 코스 추천 — 다른 추천과 무엇이 다른가

발표·심사용 정리. 전부 코드에 실제로 있는 것만 적었다(괄호 안이 위치).

## 한 줄 요약

**기차로 도착해서, 문 연 시간에, 갈 수 있는 순서로.** 포털·OTA 추천은 "여기 좋아요" 목록이고, Trailer 는 열차 시각·운영시간·동선을 맞춘 **실행 가능한 일정**을 낸다.

## 차별점 여섯 가지

### 1. 열차 시각이 코스를 결정한다
오후 3시 도착이면 첫날은 한두 곳, 오전 10시 귀가면 마지막 날은 비운다. 도착·출발 열차 시각에서 그 날 관광 가능 시간을 계산해 방문지 수와 시간창을 정한다. 기차역에 내려 시작하는 여행이라 이게 없으면 "도착 전에 관광 시작하는" 일정이 나온다. (`recommend_service._day_caps` / `_day_windows`)

### 2. 운영시간·휴무일에 맞춰 시각을 배정한다
관광지마다 오픈·마감·휴무요일을 실시간으로 받아, 체류 2시간 + 이동시간을 더해가며 방문 시각을 잡는다. 식당은 점심·저녁 시간대에 동선 근처로 끼운다. 안 맞는 곳은 차순위로 바꾼다. 단순 점수순 추천은 열 곳 중 한 곳을 닫힌 시간에 보낸다(실측 11%). Trailer 는 0건. (`recommend/scheduling.py`)

### 3. 도착지를 두 단계로 고른다
도착역을 안 정하면 AI 가 고른다. 시도 단위 테마 분포로 후보를 추리고(1단계), 후보 역 **주변을 실측**해 다시 점수를 매긴다(2단계). 시도 평균으로만 고르면 "나주역 도착인데 일정은 44km 떨어진 보성"이 된다. 큰 도는 해안권·내륙권으로 나눠 따로 후보로 낸다. 같은 권역은 한 곳만 통과시켜 한 지역 쏠림을 막는다. (`recommend/destination.py`)

### 4. 관광 데이터를 저장하지 않는다 — 그리고 API 의 빈 구멍을 메운다
관광지·운영시간·이미지는 요청마다 한국관광공사 TourAPI 를 실시간으로 부른다. DB 에 관광 데이터가 없다.

여기서 발견한 문제: 2025년 API 개편 뒤 등록된 항목은 옛 지역·분류 코드가 비어 있어 **좌표 반경 조회에 아예 안 나온다.** 해운대해수욕장·경복궁·불국사가 그렇고, 부산 관광지의 60%가 그렇다. Trailer 는 법정동 시도 단위 목록을 함께 받아 반경 안만 골라 합치고, 새 분류 체계(lclsSystm)로 테마를 붙인다. 부산역 바다 테마 후보 6곳 → 27곳. (`tour_place.live_places`, `tour_category._LCLS*`)

### 5. 부족하면 풀되, 풀었다고 말한다
시골 역은 선택 테마 관광지가 0~2곳이다. 반경을 20→35→50km 로 넓히고, 그래도 없으면 테마를 푼다. 무엇을 풀었는지 응답에 담아 앱이 사용자에게 보여준다. 조용히 엉뚱한 걸 추천하지 않는다. (`tour_place.live_places_relaxed`)

### 6. 코스 세 개가 실제로 다르다
후보를 점수 순으로 A/B/C 에 번갈아 나눠 세 코스가 겹치지 않게 만든다. 빈자리를 채울 때도 다른 코스가 쓴 곳은 뒤로 미룬다. 실측에서 세 코스가 공유하던 관광지가 평균 4.6곳 → 1.2곳으로 줄었다. (`recommend/pipeline.py`)

## 설계 원칙 — 정확해 대신 휴리스틱

코스 구성은 이론상 다중일 TSP 인데 정확해(ILP·메타휴리스틱)를 일부러 쓰지 않는다. k-means 군집 → 최근접 이웃 + 2-opt 로 코스 3개를 **1ms 안팎**에 만든다. 후보가 수십 개라 최적성 손실이 작고, 실시간 API 응답 안에 끝나야 한다. 외부 라이브러리 없이 순수 파이썬이고 결정적이라(같은 입력 → 같은 추천) 재현·디버깅이 된다.

## 정직하게 — 한계

- 이동시간은 직선거리 근사(평속 30km/h × 우회 1.3). 대중교통 시간표는 반영하지 않는다.
- 연령·그룹 적합도 표는 실데이터가 아닌 휴리스틱이다.
- 공공 API 일일 한도(운영시간 조회 1,000회/키)가 하루 처리량을 정한다. 키를 늘리는 게 유일한 해법이다.
